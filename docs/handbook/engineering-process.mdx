---
title: Engineering process
description: How a change goes from idea to merge. Same steps for people and agents.
---

The process follows pstack, but you don't need pstack installed. What counts is the evidence, not the tool.

<Callout title="What GitHub enforces">
  `Verify` and `PR contract` must pass before anything merges into `dev` or
  `main`.
</Callout>

## 1. Start from dev

```bash
git switch dev
git pull --ff-only origin dev
git switch -c feat/<short-name>
```

- One focused change per branch.
- Pull requests target `dev`. Only a release from `dev` targets `main`.

## 2. Read before you edit

1. `AGENTS.md`
2. `.agents/skills/contribute/SKILL.md`
3. `docs/README.md`
4. The feature doc in `docs/features/`
5. The architecture doc in `docs/core/`
6. `docs/design.md` and `docs/vibe.md` for UI work
7. The known-gap docs
8. The verification map in `.agents/skills/verify/features/`

## 3. Document the feature first

```bash
cp docs/features/_template.md docs/features/<feature-name>.md
```

State the outcome, scope, non-goals, user-visible states (success, waiting, refusal, failure), permissions, external services, and how you'll prove it.

- Update the doc **in the same pull request** as the code.
- Size it to the change. A one-line fix needs no design doc.

## 4. Use the pstack sequence

| Skill                                        | When                                |
| -------------------------------------------- | ----------------------------------- |
| `pstack:how`                                 | Unfamiliar code                     |
| `pstack:architect`                           | Structural or cross-cutting changes |
| `pstack:principle-sequence-verifiable-units` | Multi-step work                     |
| `pstack:technical-writing`                   | Feature and design docs             |
| `pstack:blast-radius`                        | What could this break?              |
| `pstack:deslop`                              | Remove unrelated or generated code  |
| `pstack:make-pr-easy-to-review`              | Before opening the PR               |
| `pstack:principle-prove-it-works`            | Before calling it done              |

## 5. Keep it focused

- One outcome per pull request.
- Follow existing patterns.
- Unrelated cleanup goes in its own PR.
- Update shared schemas before their consumers.
- Product changes and workflow changes ship separately.

## 6. Run the checks

Smallest relevant checks first. Before a broad merge:

```bash
pnpm format && pnpm lint && pnpm typecheck && pnpm test && pnpm build && pnpm verify:deploy-config
```

Connector changes also need:

```bash
pnpm verify:connectors
pnpm --filter @garden/connectors typecheck
pnpm --filter @garden/connectors test
```

<Callout title="What CI runs for you">
  `Verify` runs once per pull request to `dev` or `main`, and again when a
  change lands there. It skips feature-branch pushes. Want early CI? Open a
  draft PR.
</Callout>

## 7. Prove the user flow

Tests don't prove a user flow works. For UI, connector, agent, workflow, or deployment changes:

```bash
pnpm doctor                                  # read-only readiness check
pnpm offline:up                              # or offline:up:ollama
pnpm --filter @garden/db db:migrate
pnpm dev:offline                             # then open http://localhost:3000
```

Save evidence to `~/.garden/evidence/<UTC timestamp>-<scenario>/`:

- `report.md`, `report.json`, `screenshots/`
- Action, expected result, observed result, route or command
- Status: **PASS**, **FAIL**, or **INCONCLUSIVE**

<Callout type="warn">
  Didn't prove the flow? It's INCONCLUSIVE. Not PASS.
</Callout>

<Callout title="No AI evals yet">
  Prompt, skill, and tool-definition changes have no automated eval gate
  (FLO-37). Prove agent behavior with a recorded run.
</Callout>

## 8. Review your own diff

```bash
git diff --check && git status && git diff
```

- Only the intended change?
- Docs match the code?
- Permissions right? Migrations safe?
- No credentials or local files?

## 9. Open the pull request

```bash
git add <files>
git commit -m "<type>: <short description>"
git push -u origin <branch-name>
```

`PR contract` fails the PR unless it has these eight headings:

1. What changed
2. Why
3. Scope
4. Contribution standard
5. Documentation
6. Checks
7. Verification
8. Risk and follow-up

It also checks four rules:

- **Target branch**: `dev`, or `main` for a release.
- **Contribution standard**: outcome, reading, and diff-review boxes ticked.
- **Documentation**: name the docs you changed, or say why none changed.
- **Checks and verification**: list commands, state PASS / FAIL / INCONCLUSIVE, point to evidence.

Drafts only need a valid target and title. Check locally:

```bash
pnpm verify:pr --event path/to/pull-request-event.json
```

<Callout type="warn">
  The contract checks that evidence is *named*. A maintainer checks that it's
  *true*.
</Callout>

## 10. Maintainer review

**Classify** every open PR: merge now, needs changes, blocked, or superseded.

**Write the review** in this order:

1. Thank the author for the specific change.
2. **What passed**
3. **Before merge**: blockers only
4. **Follow-up**: non-blocking, kept separate
5. **Review status**: `APPROVE`, `REQUEST_CHANGES`, or `COMMENT`
6. **Next action**

Each finding:

```text
Finding:  [specific problem]
Impact:   [what can break]
Evidence: [file, test, command, log, or repro]
Request:  [exact change or check]
```

- A blocker left open means `REQUEST_CHANGES`.
- Never label a follow-up as a blocker.
- Agents recommend. A maintainer merges.

## 11. Clean up

```bash
pnpm offline:down
```

Stop only what you started. Don't reset the database unless the team agrees.
