---
title: Ship a change to dev
description: Take one focused change from a new branch to a merged pull request.
---

Every change reaches `dev` through a pull request. GitHub blocks the merge until the `Verify` and `PR contract` checks pass. These steps get a change through both checks and through review. They apply to people and agents alike.

## Create a branch from dev

```bash
git switch dev
git pull --ff-only origin dev
git switch -c feat/<short-name>
```

Keep one user or maintainer outcome per branch. Put unrelated cleanup on its own branch.

## Read the rules for the area you change

Before you edit code, read these files:

1. `AGENTS.md`
2. `.agents/skills/contribute/SKILL.md`
3. `docs/README.md`
4. The feature document in `docs/features/`
5. The architecture document in `docs/core/`
6. `docs/design.md` and `docs/vibe.md`, if you change UI
7. The verification map in `.agents/skills/verify/features/`, if your change touches a user flow

## Write the feature document first

To add a feature, copy the template:

```bash
cp docs/features/_template.md docs/features/<feature-name>.md
```

Fill in the outcome, scope, user-visible states, permissions, external services, and verification steps. Update the document in the same pull request as the code. A bug fix that changes no behavior needs no feature document.

## Run the checks that cover your change

Run the checks for the files you changed first. Before a broad change merges, run the full set:

```bash
pnpm format
pnpm lint
pnpm typecheck
pnpm test
pnpm build
pnpm verify:deploy-config
```

`pnpm format` only checks formatting. To fix formatting, run `pnpm format:write`.

If you change a connector, also run:

```bash
pnpm verify:connectors
pnpm --filter @garden/connectors test
```

CI runs the `Verify` job once for each pull request to `dev` or `main`. CI does not run on a push to a feature branch. To get CI results before the work is done, open a draft pull request.

## Prove the user flow

Passing tests do not prove that a user can complete a flow. If you change UI, a connector, an agent, a Workflow, or deployment, run the flow in a browser.

1. Check that your machine is ready:

   ```bash
   pnpm doctor
   ```

2. Start the local services and Garden:

   ```bash
   pnpm offline:up
   pnpm --filter @garden/db db:migrate
   pnpm dev:offline
   ```

3. Open `http://localhost:3000` and run the flow.
4. Save the evidence in `~/.garden/evidence/<UTC timestamp>-<scenario>/`. Include `report.md`, `report.json`, and a `screenshots/` folder.

Each report states the action, the expected result, the observed result, and a status of `PASS`, `FAIL`, or `INCONCLUSIVE`. If you could not prove the flow, the status is `INCONCLUSIVE`.

<Callout title="Prompt and tool changes">
  Garden has no automated evals yet (FLO-37). If you change a prompt, a skill,
  or a tool definition, record an agent run that shows the new behavior.
</Callout>

## Review your own diff

```bash
git diff --check
git status
git diff
```

Confirm that the diff holds only the intended change, that the documents match the code, and that no credentials or local files are staged.

## Open the pull request

Stage only the files for this change:

```bash
git add <files>
git commit -m "<type>: <short description>"
git push -u origin <branch-name>
```

Open the pull request against `dev`. Fill in every section of the template. The `PR contract` check fails the pull request if a required section or checklist item is missing. For the full list, see [Pull request contract](/handbook/pr-contract).

## Stop what you started

When verification is done, stop the local services:

```bash
pnpm offline:down
```

Don't reset the local database unless the team agrees.
