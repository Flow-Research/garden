# Garden Web

TanStack Start app for Garden's tabbed workspace, auth surface, API routes, Cloudflare Worker bindings, and local agent runtime.

## Getting Started

From the repository root:

```bash
pnpm install --frozen-lockfile
cp .env.example .env

# Fill the required values in .env, then authenticate Wrangler:
pnpm --filter @garden/web exec wrangler login
pnpm --filter @garden/web exec wrangler whoami

pnpm --filter @garden/db db:migrate
pnpm dev
```

The [root setup guide](../../README.md#run-garden-locally) explains each
required value and the two secrets you need to generate. The root dev command
starts the Garden Worker through Turbo's TUI. The web app runs at
`http://localhost:3000` by default.

## Environment

Local development configuration lives in root `.env`. Web, database tooling, and local scripts share it; deployed Workers use Cloudflare secrets and bindings.

Required for normal local development:

```bash
CLOUDFLARE_ACCOUNT_ID=<your Cloudflare account>
DATABASE_URL=postgresql://...
BETTER_AUTH_SECRET=...
EXECUTOR_SECRET_KEY=...
BETTER_AUTH_URL=http://localhost:3000
ENVIRONMENT=development
```

Authenticate Wrangler, then verify the selected account:

```bash
pnpm --filter @garden/web exec wrangler login
pnpm --filter @garden/web exec wrangler whoami
```

Workers AI has no local simulator, so normal local development uses that one
remote binding and may incur account usage. Set `AI_GATEWAY_ID` only to route
requests through an AI Gateway owned by your account.

`RESEND_API_KEY`, `EXA_API_KEY`, and connector credentials are optional until
their corresponding email, search, or connector feature is used.

## Commands

| Command                                         | Description                                                     |
| ----------------------------------------------- | --------------------------------------------------------------- |
| `pnpm --filter @garden/web dev`                 | Start local state with Sandbox containers and remote Workers AI |
| `pnpm --filter @garden/web dev:local`           | Start with local state and remote Workers AI                    |
| `pnpm --filter @garden/web build`               | Build production worker bundle                                  |
| `pnpm --filter @garden/web typecheck`           | Run TypeScript without emit                                     |
| `pnpm --filter @garden/web worker:types:check`  | Regenerate and verify Worker binding types                      |
| `pnpm --filter @garden/web skills:seed-builtin` | Seed bundled skills into the local workspace                    |

## Cloudflare Runtime

The local Worker uses `wrangler.jsonc` for Durable Objects, D1, R2, Workflows,
and sandbox bindings. Root `pnpm dev` keeps stateful bindings local while
Workers AI runs remotely. Root `pnpm dev:containers` and the direct web `dev`
command use `wrangler.containers.jsonc` to add Docker-backed Sandbox
containers; D1, R2, Durable Objects, Workflows, and Hyperdrive still run in the
local development configuration. An ignored `wrangler.containers.local.jsonc`
is available only when a developer deliberately needs account-specific
overrides. Key runtime pieces:

- `AgentDO` hosts per-agent state and WebSocket/RPC behavior.
- `FILES` stores uploaded files; `LOADER` supplies isolated Executor and agent code execution.
- `RUN_WORKFLOW` drives durable issue-run and automation-run execution directly from `AgentDO`.
- Executor is composed directly inside the Garden Worker. `EXECUTOR_DB`,
  `EXECUTOR_BLOBS`, `EXECUTOR_MCP_SESSION`, and
  `EXECUTOR_MCP_EXECUTION_OWNER` provide its persistence and MCP runtime. The
  public SDK supplies the engine; exact upstream source is retained only for
  unpublished Cloudflare host pieces.
- Sandbox containers are enabled by `pnpm dev:containers` or the direct web
  `dev` command via `wrangler.containers.jsonc`; normal `pnpm dev` skips
  containers.

Generated files such as `src/routeTree.gen.ts` and Worker types should be regenerated by the relevant scripts, not hand-edited.

## Manual Smoke

If you already use the optional `agent-browser` CLI, it can drive a real app
check in addition to the unit suite. It is not installed by this repository:

```bash
pnpm --filter @garden/web dev:local
agent-browser --session garden-smoke open http://localhost:3000/workspace
agent-browser --session garden-smoke snapshot -i -c -d 3
agent-browser --session garden-smoke console
agent-browser --session garden-smoke errors
```

Useful authenticated endpoint sweep:

```bash
curl -fsS http://localhost:3000/api/me
curl -fsS http://localhost:3000/api/workspaces
curl -fsS http://localhost:3000/api/issues
curl -fsS http://localhost:3000/api/inbox
curl -fsS http://localhost:3000/api/agents
curl -fsS http://localhost:3000/api/skills
curl -fsS http://localhost:3000/api/connections
```

Browser-session auth is usually easier through `agent-browser`; plain `curl` needs the same local auth cookies.
